# ADR-0006: 聚合主键改用 UUID v7（应用侧生成）

## 状态

已接受 (Accepted) — 2026-10

## 上下文 (Context)

脚手架原实现用数据库自增主键，由此派生出一整套"补丁式"约定：

| 现象 | 根因 |
| --- | --- |
| `Order.attachId(Long)`——javadoc 标明"仅供仓储调用"的公开 setter | 聚合在工厂方法里没有身份，只能等仓储插入后回填，封装被迫开洞 |
| `save()` 里 `order.attachId(orderDO.getId())` | 仓储为了回填必须持有可变聚合 |
| Jackson 全局 `Long → String` 序列化 | 64 位自增/雪花 ID 出到前端丢 JS 精度 |
| README 承诺"生产替换为雪花 ID/号段模式" | 多实例唯一性要额外基础设施，自增本身不满足 |

自增主键还顺带暴露业务量级（竞品可据 ID 增量估算单量），且分库分表时是长期负担。

## 决策 (Decision)

1. **主键统一为 UUID v7 字符串**，由 `domain/support/Ids` 在领域工厂方法内生成（应用侧身份）；
2. `Order.create()` 创建即拥有 ID，**删除 `attachId()`**；`restore()` 保留（仅仓储重建用）；
3. 仓储 `save()` 只负责持久化，不再回填任何字段；MyBatis 插入去掉 `useGeneratedKeys`；
4. 明细主键同策略，由 `OrderConverter` 在落库前统一分配（明细 ID 是持久化细节，不进领域模型）；
5. `domain/support/PageLimits` 收敛分页上限为单一事实源，api 校验注解与仓储兜底钳制共同引用。

## 为什么是 UUID v7 而不是 UUID v4 / 雪花 / 号段

| 方案 | 结论 |
| --- | --- |
| UUID v4 | 完全随机，主键索引页分裂严重，大表写入性能差 |
| 雪花 / 号段 | 需要额外基础设施（worker id 分配、号段服务），与"轻量"目标冲突 |
| **UUID v7** | 时间戳在高 48 位，**字典序≈时间序**，B-tree 友好；应用侧生成零依赖；`Ids` 用 rand_a 做同毫秒递增序号，进程内严格单调 |

## 后果 (Consequences)

### 正向收益

- 聚合创建即完整，`attachId()` 这类"仅供仓储调用"的封装破洞消失；
- 多实例唯一性天然成立，不再需要雪花/号段基础设施；
- 主键对外即字符串，精度问题在主键层面消解；
- 排序语义明确：`ORDER BY gmt_create DESC, id DESC`，不依赖 ID 文本序。

### 代价与缓解

- 存储 36 字节 vs 8 字节：可接受；若未来需要压缩，改用 `BINARY(16)` 是基础设施层局部改动，不影响领域；
- `Ids` 引入了一个带锁的静态临界区：锁只保护毫秒戳+序号两个 long 赋值，纳秒级；实测万次生成无重复；
- 存量库迁移需新增字符串主键列并回填：新项目无此问题。

## 备选方案（已否决）

- 保留自增 + 继续用 `attachId()`：把封装破洞当常态，否决；
- 只用 UUID v4：索引写入劣化，否决；
- 引入雪花算法：为一个脚手架引入号段/worker 基础设施，过度设计，否决。
