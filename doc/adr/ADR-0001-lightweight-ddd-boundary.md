# ADR-0001: 轻量 DDD 架构边界与裁剪决策

## 状态

已接受 (Accepted) — 2026-09

## 上下文 (Context)

在企业级 Java 项目中，DDD 常被过度工程化：

1. 盲目拆分多 Maven 模块（`client` / `app` / `domain` / `infra` / `start`），
   一个简单需求需跨 5 个模块修改代码与 POM，开发跳转与编译构建极慢；
2. 强引入重型专用框架（如 COLA、Axon、Eventuate 等），导致领域业务代码与第三方商业或开源框架深度绑定；
3. 过早引入严格 CQRS（读写双模型/两套库）和 Event Sourcing（事件溯源），导致一致性保障成本飙升。

团队需要一套既能享受 DDD 战术设计（充血模型、不变量、依赖倒置）带来的业务防腐收益，又保持单体 Maven 极高开发吞吐效率的标准化脚手架。

## 决策 (Decision)

1. **单模块 + 规范包分层**：使用单 Maven 模块组织代码，按 `api`、`application`、`domain`、
   `infrastructure` 四层包严格划分；
2. **ArchUnit 架构守护**：不依赖 Maven 物理模块隔离，改用 `ArchUnit` 在测试阶段强制执行依赖规则。写错依赖方向直接构建失败；
3. **零 DDD 专有框架**：不引入 COLA 或任何专有框架，纯靠架构分层和标准 Java 表达；
4. **裁剪 CQRS 与事件溯源**：持久化采用实用主义单库模型，读操作走仓储装载，业务并发通过 DB CAS 解决，不维护两套模型。

## 后果 (Consequences)

### 正向收益

- 极快编译构建速度，改动一个字段可在单一项目内闭环；
- 架构规则由 CI 守护测试强制约束，保障团队不走形；
- 业务内核与任何第三方框架解耦，技术选型生命周期长。

### 潜在风险与应对

- 多个聚合根并存时，若包划分不清可能出现横向交织。应对：`ArchitectureTest` 配置包切片无环规则（`freeOfCycles`）。
